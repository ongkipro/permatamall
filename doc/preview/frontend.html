Standalone Frontend

Frontend bebas, kontrak commerce tetap satu.

CMSAds mendukung mode integrated dan headless. Setiap tenant boleh memilih presentasi yang berbeda, sementara data, checkout, order, shipping, payment, dan tracking tetap berada pada backend tenant yang terisolasi.

Topology Headless vs Integrated

Pemisahan tanggung jawab secara eksplisit antara presentation dan core business logic.

Integrated

Satu Worker CMSAds memiliki Custom Domain dan merender storefront, form, admin, serta API. Mode ini tetap didukung untuk tenant yang ingin satu deployment.

Implemented

Headless

Worker storefront memiliki domain publik. Backend CMSAds memakai service-only dan menerima route operasional melalui private service binding. Arsitektur ini didukung, tetapi belum memiliki active reference deployment.

Separate Frontend Worker via Service Binding

Komunikasi internal antar-worker tanpa overhead jaringan publik.

Service Binding

Frontend tenant dijalankan sebagai Worker mandiri dan meneruskan route operasional ke binding CMSADS. Browser tetap memakai origin tenant; backend service-only tidak memiliki public route.

const CMSADS_PATHS = ['/admin', '/api', '/hello', '/thanks', '/hybrid-form', '/middle-form', '/full-form'];

export default {
  fetch(request, env) {
    const path = new URL(request.url).pathname;
    return CMSADS_PATHS.some((prefix) => path === prefix || path.startsWith(`${prefix}/`))
      ? env.CMSADS.fetch(request)
      : env.ASSETS.fetch(request);
  }
};

Storefront Integration Prompt Boundary

Integrasi UI public menggunakan AI generation wajib berdasarkan data dinamis, bukan sekadar fallback palsu.

Dynamic Catalog Prerequisite

Prompt integrasi storefront (disimpan dalam STOREFRONT_INTEGRATION.md) mengatur bahwa catalog atau product bootstrap dari API CMSAds adalah prerequisite wajib. AI generation tidak boleh membuat fake static fallback jika API katalog tidak dikonfigurasi, memastikan semua order di public layout disinkronisasikan ke backend yang tepat.

No Cross-Tenant Data Copy

Isolasi berasal dari resource Cloudflare per deployment, bukan filter hostname runtime.

  • D1, R2, KV, Workers AI, dan secret berbeda untuk setiap tenant.
  • Installer tidak mengimpor data tenant yang sudah ada.
  • Deploy frontend tidak memigrasikan D1 atau men-deploy backend.
  • Penghapusan Worker atau storage selalu operasi terpisah yang memerlukan approval eksplisit.

Workflow AI Storefront

Mempercepat pembuatan komponen dan halaman e-commerce menggunakan AI Agent.

Tahap Aksi Role/Sistem
1. Generasi Prompt Merchant mendeskripsikan kebutuhan campaign atau komponen (misal: "Bikin landing page promo ramadan"). Merchant / Operator
2. AI Drafting AI membuat draft struktur HTML/Astro dan copy, mematuhi rule desain tenant. Workbench implemented CMSAds AI / Cloudflare Workers AI
3. Review & Edit Draft tidak langsung tayang. Operator memeriksa, menguji di environment terisolasi, atau merevisi instruksi. Operator
4. Handoff & Release Agent mengimplementasikan di repository pemilik frontend, menjalankan test/build/dry-run dan browser proof, lalu berhenti di approval gate sebelum deploy. AI Agent + Operator
